Relationships, grain and business definitions

A key relationship explains how tables connect. It does not fully explain what one row represents or what a measure means to the business. An assistant can produce plausible SQL while misunderstanding the intended grain.

I built and internally deployed a Claude Code CLI context harness. My team uses it to investigate defects and write or fix code with schema-derived relationships, table grain and business annotations I author by hand.

Context design and review

01 / Generate

Schema-derived context

Schema metadata supplies the structural map: key relationships and table grain. It gives the assistant context for reasoning across tables.

02 / Annotate

Authored business definitions

I add business meaning manually. The annotations capture domain knowledge that key relationships alone cannot supply.

03 / Validate

Engineering review and tests

The harness supplies context; engineers still review and test AI-assisted SQL and code changes.

Team use and maintenance

The team uses the harness as shared context for AI-assisted SQL and defect diagnosis. The design makes both structural information and authored business meaning available in the engineering workflow.

Business annotations require maintenance as schema and domain rules change. I keep that responsibility explicit instead of assuming metadata generation supplies all the meaning.

Internal schema and business annotations remain private. Figures use generic concepts and fictional records.
