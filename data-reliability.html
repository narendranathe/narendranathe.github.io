Correct data. Recoverable runs.

I work on the SQL Server and Azure workflows behind HR and payroll reporting: moving changes, checking data, investigating failures, and recovering the incremental path.

What was at stake

A load can finish while the data is still wrong. In HR and payroll reporting, stale or inconsistent data affects the people interpreting the report. Full-table reloads also repeat work on records that have not changed.

My responsibility included changing the ingestion pattern and making failures more understandable. I reengineered full reloads into idempotent incremental merge-upserts, built configuration-driven checks, and created a separate SQL procedure for failed-job evidence.

A schematic of related responsibilities

The decisions behind the design

01 / Data movement

Process changes. Plan for reruns.

I changed the CDC path from full reloads to incremental merge-upserts. The key requirement was repeatability: a failed run needed to rerun cleanly, without manual cleanup of half-applied data.

The tradeoff is state. An incremental path needs more careful handling of change tracking and partial runs than a full reload. Idempotency is part of the design, not something a retry button adds.

02 / Correctness

Make checks configuration.

I built a validation framework driven by a control table. A new check is defined in configuration rather than becoming another standalone script to maintain.

This makes the framework extensible, but the rules still need engineering judgment: someone must decide what correct data means. The recorded deployment is in a shared test environment.

03 / Investigation

Keep evidence close to the failure.

I built a separate stored procedure that reads SSISDB: which packages ran, when they ran, and execution evidence around failed SQL Agent jobs.

It gives the team information for targeted fixes. Detection and evidence gathering are separate from recovery automation; this procedure does not automatically retry the job.

Ownership after the first successful run

Restore the path people depend on.

I diagnosed a live incremental-load failure and restored the incremental path in place, without falling back to a full reload. I also document CDC and availability-group recovery procedures so the response can be followed by another engineer.

Make delivery repeatable too.

I own Azure DevOps release automation, including SSRS and Power BI deployment steps, and coordinate changes across development, test, IT, and business. Python workflows using Git and Azure DevOps APIs supply delivery visibility. AI-assisted code goes through review and tests.

What changed, and why it mattered

The ingestion path became incremental and rerunnable. Validation rules gained a shared configuration mechanism. Failed-job investigations gained package-level execution evidence. These are different improvements to the same responsibility: help engineers understand and operate the data that reporting teams depend on.

The shared-test validation framework and the SSISDB diagnostic procedure address different questions: is the data right, and what happened during execution? Engineers use that context to investigate and recover.

Employer code and operational records are private. This architecture is a public-safe schematic; it shows responsibilities, not proprietary infrastructure.

Questions I can walk through in an interview

Why incremental loads need idempotency; what can go wrong in a partial run; how a control-table-driven framework can grow without a collection of disconnected scripts; what SSISDB reveals about package execution; and how I approached a live incremental failure.
