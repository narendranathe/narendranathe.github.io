# Skills Grid — categorized monogram tiles with hover tooltips

A small accessible HTML+CSS pattern for displaying a recruiter-scannable inventory of tools, organized by domain, with one-line context revealed on hover or focus. Designed to be senior-engineer credible (no sticker-book CV gimmick) and copy-pasteable into any portfolio (Hugo, Jekyll, Next.js, Astro, vanilla HTML).

> **Why this exists:** Project tech-chips show stack on a per-project basis. A page-wide skill inventory communicates breadth, but the typical "wall of color logos" reads as a CV gimmick. This pattern replaces logos with monochrome monogram tiles that flow with the site's typography and palette, plus a hover-revealed one-line context so each tile is defensible at first follow-up question.

**Status:** `v0.1.0-experimental`. Used in production at `narendranathe.github.io`. Class names may change before v1.

## The HTML

```html
<section class="section" id="skills">
  <div class="container">

    <div class="section-head">
      <span class="section-label">Stack</span>
      <h2 class="section-title">Stack I work in daily.</h2>
      <p class="section-subtitle">Hover or focus a tile for one-line context.</p>
    </div>

    <div class="skills-grid">
      <div class="skills-category">
        <h3 class="skills-category-title">AI &amp; LLM Stack</h3>
        <ul class="skills-list">
          <li>
            <button type="button" class="skill-icon"
                    aria-describedby="skill-tip-claude"
                    aria-label="Claude">
              <img src="/static/skills/claude.svg" alt=""
                   width="48" height="48"
                   loading="lazy" decoding="async"
                   class="skill-glyph">
              <span class="skill-name">Claude</span>
              <span id="skill-tip-claude" role="tooltip" class="skill-tooltip">
                Primary LLM in production cascade
              </span>
            </button>
          </li>
          <!-- 4-6 tiles per category -->
        </ul>
      </div>
      <!-- 4-6 categories -->
    </div>

  </div>
</section>
```

**Why `<button type="button">` not `<a>` or `<div>`** — each tile has no destination URL but must be focusable for keyboard navigation and have a clear interactive role for screen readers. `<button>` is the right semantic; `<a>` without an `href` is invalid. WCAG 2.1.1 (Keyboard).

**Why `<img>` not inline `<svg>`** — the SVG monograms are static assets in `static/skills/`, allowing browser caching across pages and lazy-loading off-screen tiles. Inline SVG would inflate the HTML payload by ~10 KB and lose the cache benefit. The `alt=""` (empty) is correct because the surrounding `aria-label` on the button provides the accessible name; the `<img>` is decorative within an already-labeled control.

**Why `aria-describedby` not `aria-label` for the tooltip** — `aria-label` would replace the button's accessible name with the tooltip text, hiding the visible "Claude" label from screen readers. `aria-describedby` adds the tooltip as a *description* alongside the label. WAI-ARIA APG canonical tooltip pattern.

**Why `role="tooltip"` on the span** — declares the element's purpose so screen readers announce "tooltip" before reading the content, preserving the hover/focus relationship. Better-tested in NVDA / VoiceOver than the newer popover-API `role="dialog"` for short hint text.

## The SVG monograms

Each `static/skills/<slug>.svg` is a 48×48 viewBox containing a centered monogram in JetBrains Mono, with `fill="currentColor"` so the tile inherits the site's text color (dark/light/print all flow naturally).

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 48 48"
     fill="currentColor" aria-hidden="true">
  <rect x="2" y="2" width="44" height="44" rx="9"
        fill="none" stroke="currentColor" stroke-width="1.4"
        opacity="0.42"/>
  <text x="24" y="30" text-anchor="middle"
        font-family="'JetBrains Mono',ui-monospace,monospace"
        font-size="18" font-weight="600" letter-spacing="0.5"
        fill="currentColor">Py</text>
</svg>
```

**Why monograms not branded logos** — half of any senior portfolio's stack carries trademark or brand-use restrictions (Anthropic Claude, OpenAI, AWS, Azure, Microsoft Fabric, GitHub) that monochrome `currentColor` rendering does NOT mitigate. Recoloring a trademarked mark is sometimes *more* problematic than not using it (AWS / Microsoft brand guidelines explicitly forbid recoloring). Hand-rolled monograms are 100% original IP, dark-mode safe, and read as elegant when a wall of color logos would not. They also load uniformly in ~250-400 bytes each.

**Reproducibility** — all 27 SVGs in this portfolio's grid are generated by `scripts/snap-skills.py`. To add a new tile, append to the `SKILLS` list and re-run; bytes are stable across runs.

## The CSS

```css
.skills-grid {
  display: flex;
  flex-direction: column;
  gap: 2.25rem;
}

.skills-category-title {
  font-family: 'JetBrains Mono', ui-monospace, monospace;
  font-size: 0.72rem;
  font-weight: 500;
  letter-spacing: 0.14em;
  text-transform: uppercase;
  color: var(--fg-muted);
}

.skills-list {
  list-style: none;
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(110px, 1fr));
  gap: 0.55rem;
}

.skills-list > li { display: contents; }

.skill-icon {
  position: relative;
  display: flex; flex-direction: column;
  align-items: center; gap: 0.45rem;
  min-height: 92px;
  padding: 0.85rem 0.55rem 0.7rem;
  background: var(--bg);
  border: 1px solid var(--border);
  border-radius: var(--r);
  color: var(--fg-muted);
  transition: border-color 200ms, color 200ms,
              background 200ms, transform 200ms;
}

.skill-icon:hover,
.skill-icon:focus-visible {
  border-color: var(--accent-warm);
  color: var(--fg);
  background: var(--bg-alt);
  transform: translateY(-1px);
}

.skill-tooltip {
  position: absolute;
  bottom: calc(100% + 8px);
  left: 50%;
  transform: translateX(-50%) translateY(4px);
  background: var(--fg);
  color: var(--bg);
  padding: 0.55rem 0.7rem;
  border-radius: var(--r);
  opacity: 0;
  pointer-events: none;
  transition: opacity 180ms, transform 180ms;
}

.skill-icon:hover > .skill-tooltip,
.skill-icon:focus-visible > .skill-tooltip {
  opacity: 1;
  transform: translateX(-50%) translateY(0);
}

@media (max-width: 780px) {
  /* Mobile: tooltip collapses to inline static caption — no hover gesture
     needed for touch users. Same DOM, divergent layout. */
  .skill-tooltip {
    position: static; transform: none;
    opacity: 1; pointer-events: auto;
    background: transparent; color: var(--fg-soft);
    box-shadow: none; padding: 0;
  }
}

@media (prefers-reduced-motion: reduce) {
  .skill-icon { transition: none; }
  .skill-tooltip { transition: none; }
}

@media print {
  .skill-tooltip {
    position: static; transform: none;
    opacity: 1; background: transparent; color: #555;
  }
}
```

**Why CSS-only show/hide (no JS)** — the M1 hover-preview popover state machine (~200 LOC) is over-engineered for plain text tooltips. CSS-only `:hover` + `:focus-visible` covers every interaction the tooltip needs: keyboard focus, mouse hover, and the `aria-describedby` association is purely declarative. WAI-ARIA APG cautions against custom JS tooltip implementations precisely because they often miss the keyboard path; CSS-only avoids that trap.

**Why `display: contents` on `<li>`** — the `<ul>` semantically groups the tiles for screen readers ("list, 6 items"), but the visual layout is a CSS Grid where `<li>` boxes would interfere with the auto-fill column rhythm. `display: contents` removes the `<li>` from the box tree without breaking the list semantics. Supported in all modern browsers as of 2024.

**Why mobile drops the popover entirely** — touch devices have no hover state; a tap-then-tap pattern (tap to show tooltip, tap again to dismiss) would conflict with the button's `:focus-visible` semantics and create double-tap confusion on adjacent tiles. Static inline captions on mobile are accessible to everyone (touch, screen reader, keyboard) without any state machine.

## Categories

Five categories proven to scan in three seconds for senior AI/ML platform recruiters in 2026:

1. **AI & LLM Stack** — model APIs, retrieval primitives, agent protocols
2. **Languages & Frameworks** — primary language(s) + frameworks/libraries that ship every service
3. **Data & Storage** — OLTP store, cache, streaming layer, lakehouse, vector store
4. **Cloud & Deployment** — cloud provider(s), container runtime, orchestration, edge platform
5. **Observability & Ops** — metrics, logs, errors, experiment tracking, CI

Categories are ordered by *relevance to the role being targeted*, NOT alphabetically. AI engineering targets see "AI & LLM Stack" first; backend-platform targets would reorder Languages first.

**Avoid these category mistakes:**
- "Tools / IDEs" (Cursor, Claude Code, Copilot) — reads as junior; signals tool-user, not system-builder
- A grab-bag "Other" — better to drop the tool than create a category-of-shame
- Including a tool from a project that no longer ships — creates a citation gap at the technical screen

## Honest tradeoffs

- **Recognizability < credibility.** Most recruiters can identify "Py" + "Python" caption faster than they can identify the Python logo at 28×28. Monograms are also easier to remember as you scan 27 in a row.
- **Touch experience is text-heavy.** On mobile, every tile shows icon + name + context inline, which makes the section ~2× taller than the desktop grid. Acceptable trade for serving the "stack match in 3s" goal on every device.
- **Tooltips clip at edges.** The rightmost tile in a row will have its tooltip overflow the viewport on small screens. The mobile `position: static` collapse fixes this; on desktop with narrow viewports, the absolute-positioned tooltip can extend past the column. A future refinement could add `inset-inline-start` flipping for edge tiles, but for the current grid widths this hasn't been a real problem.
- **No dark-mode brand colors.** When dark mode lands, monograms in `currentColor` adapt automatically, but they will *never* show the iconic green-elephant-Postgres or orange-AWS color associations a recruiter might subconsciously expect. The pattern bets that consistency wins over recognition.

## Drop-in checklist for adopters

1. Copy `static/skills/` SVGs (or generate your own via `scripts/snap-skills.py`)
2. Copy the `.skills-grid` / `.skill-icon` / `.skill-tooltip` CSS module
3. Insert the `<section id="skills">` HTML scaffold in your home page
4. Add a "Stack" link in your nav between the most-relevant adjacent items
5. Add the structural assertions in `scripts/test-portfolio.py` (or your equivalent) so future regressions of the regression-prone CDN-dependency, missing-aria-label, or oversize-icon failures get caught in CI
6. Audit your tool list against the "category mistakes" above before publishing
