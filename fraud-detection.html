Pipeline architecture

The Kafka consumer sends batches through a reusable HTTP session to FastAPI. Predictions reach PostgreSQL through pooled connections and bulk inserts. LightGBM training and MLflow tracking sit alongside the serving path.

Prometheus and Grafana provide operational visibility. The dataset contains 100,000 synthetic transactions; this is an independent engineering project.

Batching, persistence and model evaluation

01 / Persistence

Idempotent PostgreSQL inserts

ON CONFLICT (transaction_id) DO NOTHING prevents another stored row for an existing ID. Kafka offsets are auto-committed, so the persistence safeguard does not establish exactly-once processing across the pipeline.

02 / Serving

Batch requests and bulk writes

HTTP-session reuse, connection pooling and bulk insertion reduce repeated setup in the implementation. Current end-to-end throughput has not been benchmarked.

03 / Evaluation

Threshold tuning and evaluation

The displayed held-out split is also used for threshold selection. A separate final test set is needed for a stronger estimate of model performance.
