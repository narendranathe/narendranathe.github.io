Independent project · Synthetic data · Local demonstration

A fraud-scoring pipeline on synthetic data

An independent Kafka, FastAPI, LightGBM, and PostgreSQL demonstration for exploring scoring, duplicate handling, and operational visibility together.

Reviewed source Consumer API

The engineering question

I used a generated transaction dataset to work through the boundaries between ingestion, model serving, persistence, and monitoring. The intended reviewer is another engineer inspecting those boundaries. No payment processor or fraud team is claimed as a user.

What I built

The current consumer sends batches to FastAPI through a reusable HTTP session. Predictions are written to PostgreSQL through a connection pool and bulk inserts. LightGBM training and MLflow tracking sit alongside the serving path; Prometheus and Grafana provide operational visibility.

A concrete decision: duplicates

Writes use ON CONFLICT (transaction_id) DO NOTHING, so replaying an already stored transaction does not create another prediction row. Kafka offsets are auto-committed. Idempotent inserts do not establish exactly-once or lossless end-to-end delivery.

Model and data boundaries

The dataset contains 100,000 generated transactions, not live payment traffic. Training uses a cost-weighted decision threshold and the API loads the saved threshold. The reviewed threshold selection uses the displayed held-out split rather than a separately established final test set, so I do not present it as a clean final model-quality evaluation.

A missing model can invoke a rule fallback. A useful next validation is to make that mode explicit in the result and verify the trained-model path separately.

Current validation and limitations

Source review confirms batching, pooling, bulk inserts, threshold persistence, and duplicate handling. Earlier latency figures describe a historical pre-batching local run; current end-to-end throughput has not been benchmarked in this review.

The Airflow directories are scaffolding with no implemented DAG. I do not claim Airflow orchestration, production deployment, real fraud prevention, or commercial model experience from this project.

Inspect and reproduce

Start with the repository's README and Compose configuration, then inspect the consumer, training, and API files together. Some README setup and architecture text predates the batching fix. I have not executed the full stack in this review, so its instructions are not marked as a newly verified reproduction.

The next proof I would add is a bounded end-to-end run with a declared machine, model mode, source record count, unique persisted count, and failure/replay checks. A producer rate alone is not a serving-throughput result.
