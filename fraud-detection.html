The path I implemented.

The consumer sends batches through a reusable HTTP session to FastAPI. Predictions reach PostgreSQL through pooled connections and bulk inserts. LightGBM training and MLflow tracking sit alongside the serving path.

Prometheus and Grafana provide operational visibility. The dataset is generated, so this project is engineering practice rather than evidence of commercial fraud prevention.

Small choices at the boundaries.

01 / Replay behavior

Ignore a duplicate insert.

ON CONFLICT (transaction_id) DO NOTHING prevents another stored row for an existing ID. That does not guarantee exactly-once processing across the pipeline.

02 / Serving overhead

Batch requests and writes.

HTTP-session reuse, connection pooling, and bulk insertion reduce repeated setup in the implementation. Current end-to-end throughput is not benchmarked here.

03 / Evaluation

Keep the model claim narrow.

Threshold selection uses the displayed held-out split. Without a separate final test set or real traffic, I do not present a final production-quality score.

Follow the code, then test the boundaries.

Reviewed source Repository and setup

The stack has not been rerun for this portfolio. Kafka offsets are auto-committed, a missing model can trigger a rule fallback, and the Airflow folders contain no implemented DAG. No live deployment or current latency is claimed.

What I would validate next

Run a bounded end-to-end check with a declared machine, model mode, source record count, unique persisted count, and failure/replay tests. A producer rate alone is not serving throughput. Verify the trained-model path separately from fallback behavior.

Start with the repository README and Compose configuration, then inspect consumer, API, training, and persistence together. Some setup text predates the batching change; this page does not certify a fresh reproduction.
